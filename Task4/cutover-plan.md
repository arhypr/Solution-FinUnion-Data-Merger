# Cutover-план: домен «Клиентские данные»

## Область cutover

Переключение клиентских мастер-данных на **MDM Customer Hub**:

- FU CRM и RB CRM → MDM;
- MDM → FU CRM, RB CRM, FU Core, RB Core, DWH;
- единый `party_id` становится обязательным для аналитики и отчётности.

## Роли

| Роль                          | Ответственность                                 |
|-------------------------------|-------------------------------------------------|
| Cutover Manager               | Координация, go/no-go, коммуникации             |
| Data Owner (клиентский домен) | Бизнес-решение, приёмка                         |
| Data Steward                  | Матчинг, разбор конфликтов, сверка              |
| Platform Team                 | MDM, Kafka, ESB, DWH                            |
| ИБ                            | Проверка доступа, маскирования, аудита          |
| BI / Reporting                | Проверка витрин и отчётности                    |
| Support / Contact Center      | Обработка клиентских обращений в период cutover |

## Таймлайн cutover (T — время переключения)

| Время     | Шаг                    | Действие                                                                                   |
|-----------|------------------------|--------------------------------------------------------------------------------------------|
| T-10 дней | Подготовка             | Проверка готовности MDM, Kafka, DWH; прогон cutover на стенде; резервные копии             |
| T-3 дня   | Pre-check              | Сверка количества клиентов, тестовый матчинг, проверка rollback                            |
| T-1 день  | Go/No-Go               | Решение о старте; коммуникация командам                                                    |
| T-2 часа  | Soft freeze            | Новые клиенты и изменения клиентских данных пишутся в очередь; операции не останавливаются |
| T         | Финальная выгрузка     | Выгрузка клиентов из FU CRM и RB CRM, ссылок из Core                                       |
| T+30 мин  | Загрузка               | Загрузка в MDM staging                                                                     |
| T+1 час   | Матчинг и дедупликация | Правила: ФИО + ДР + ИНН + телефон + email; ручной разбор спорных                           |
| T+2 часа  | Сверка                 | Контрольные суммы и бизнес-проверки                                                        |
| T+3 часа  | Переключение           | Потребители начинают читать `party_id` из MDM; очередь изменений применяется               |
| T+4 часа  | Мониторинг             | 72 часа наблюдения                                                                         |
| T+72 часа | Закрытие               | Подписание акта cutover или rollback                                                       |

## Data freeze

- **Soft freeze:** клиентские мастер-данные нельзя менять напрямую в MDM.
- Новые клиенты и изменения в CRM разрешены, но попадают в очередь Kafka и применяются после переключения.
- Платежи, карточные операции, кредитные платежи **не останавливаются**.
- Окно soft freeze — не более 4 часов.

## Финальная выгрузка

Выгружаются:

- клиенты из FU CRM и RB CRM (ФИО/наименование, ИНН, паспорт/ЕГРЮЛ, телефон, email, адрес, сегмент, KYC-статус);
- ссылки `client_id` из FU Core и RB Core;
- согласия и блокировки по 152-ФЗ;
- справочники сегментов и отделений из RDM.

## Загрузка

- Формат: JSON/Avro по схеме MDM.
- Загрузка в staging MDM, валидация схемы и обязательных полей.
- Ошибочные записи — в DLQ, разбор Data Steward.

## Сверка (reconciliation)

| Проверка                          | Критерий                                  |
|-----------------------------------|-------------------------------------------|
| Количество клиентов по источникам | Совпадает с выгрузкой                     |
| Количество golden records         | ≤ количества источников, дубли объединены |
| Уникальность ИНН                  | 0 критичных дублей                        |
| Заполненность обязательных полей  | ≥ 99,5%                                   |
| Согласия и блокировки             | 100% перенесены                           |
| Сверка `party_id` в Core          | 100% активных клиентов связаны            |
| Выборочная ручная проверка        | 100 записей, 0 ошибок                     |
| Контрольные суммы                 | Совпадают с источником                    |

## Переключение потоков

1. MDM начинает публиковать `party_id` в Kafka.
2. FU CRM, RB CRM, FU Core, RB Core, DWH переключаются на чтение `party_id` из MDM.
3. Очередь изменений применяется к MDM.
4. DWH строит `mart_customers` и Customer 360 по golden record.
5. BI переключается на новую витрину.

## Rollback

Rollback выполняется, если:

- сверка не прошла по критичным полям;
- доля неразрешённых матчей > 1%;
- MDM не публикует события;
- DWH не строит витрины;
- ИБ фиксирует критичное нарушение.

Действия rollback:

1. Остановить публикацию `party_id`.
2. Вернуть потребителей на чтение `client_id` из CRM/Core.
3. Оставить MDM в режиме чтения для анализа.
4. Применить очередь изменений в исходные CRM.
5. Зафиксировать инцидент и назначить повторный cutover.

## Мониторинг после переключения

- Kafka lag по `party_id`.
- Доля неразрешённых матчей.
- Количество golden records и дублей.
- Ошибки в DLQ.
- Свежесть `mart_customers`.
- Обращения клиентов, связанные с профилем.
- Аудит доступа к ПДн.
- Расхождения в отчётности.

## Критерии успеха

- 0 критичных дублей.
- 100% активных клиентов с `party_id`.
- Сверка подписана Data Owner.
- 72 часа без критичных инцидентов.
- BI и отчётность работают на новых витринах.
- ИБ подтверждает корректность доступа и маскирования.
