# План миграции, cutover и технологическая дорожная карта

## Цель

Разработать план перехода от As-Is к целевой архитектуре из Task3:
этапы миграции, cutover-план для критичного домена, риски, фолбэки и технологическую дорожную карту на 12 месяцев.

## Состав

- `migration-target-state.md` — образ целевого результата: что остаётся, что выводится, что мигрирует, какие потоки
  переключаются, критерии завершения.
- `migration-plan.md` — инкрементальный план из 8 этапов с результатами и exit criteria.
- `cutover-plan.md` — cutover для домена «Клиентские данные» (MDM Customer Hub): подготовка, data freeze, финальная
  выгрузка, загрузка, сверка, переключение, фолбэк, мониторинг.
- `migration-risks.md` — реестр рисков миграции с митигацией.
- `tech-roadmap.md` — технологическая дорожная карта по зонам Adopt / Trial / Assess / Hold.
- `diagrams/migration-gantt.puml` — Gantt-диаграмма миграции.
- `diagrams/cutover-customer.puml` — Activity-диаграмма cutover клиентских данных.
- `diagrams/tech-roadmap.puml` — Mindmap технологической дорожной карты.

## Ключевые решения

1. Миграция выполняется волнами: сначала интеграционный фундамент и MDM, затем отчётность, затем консолидация Cards →
   Loans → Core, затем вывод RB legacy.
2. Клиентские данные — первый критичный cutover, потому что от них зависят CRM, Core, DWH, BI и антифрод.
3. Полная остановка сервисов недопустима: используется soft freeze и очередь изменений, а не остановка операций.
4. Cutover выполняется по контрольным суммам и бизнес-проверкам; rollback-план обязателен.
5. DWH PostgreSQL и Lakehouse внедряются параллельно: DWH — для регуляторики и быстрого результата, Lakehouse — для
   истории и событий.
6. RB Core / RB Cards / RB Loans выводятся из эксплуатации только после успешных волн консолидации и сверки отчётности.
7. DataHub и lineage — обязательные условия cutover, иначе невозможно доказать корректность данных регулятору.

## Допущения

- Cutover клиентских данных выполняется в выходные с минимальной нагрузкой, но без остановки платежей и карточных
  операций.
- Новые клиенты в период soft freeze создаются в CRM и попадают в очередь; MDM применяет их после переключения.
- Для cutover выделяется окно 4–6 часов; при превышении — автоматический rollback.
- Регуляторная отчётность в период cutover строится из старого DWH-пайплайна до подтверждения сверки.
