# DWH на PostgreSQL vs Data Lakehouse

## Сравнение для кейса FinUnion + RetailBank

| Критерий                | DWH на PostgreSQL                              | Data Lakehouse (Iceberg + Trino)                   |
|-------------------------|------------------------------------------------|----------------------------------------------------|
| Основной сценарий       | Регламентированная и управленческая отчётность | История, события, ML, полуструктурированные данные |
| Тип данных              | Структурированные                              | Структурированные, полу- и неструктурированные     |
| Объём                   | До десятков ТБ                                 | Сотни ТБ — ПБ                                      |
| Масштабирование         | Вертикальное, ограниченное                     | Горизонтальное, дешёвое                            |
| ACID                    | Да                                             | Да, через Iceberg                                  |
| Time travel             | Ограниченно                                    | Да (Iceberg snapshots)                             |
| ML                      | Ограниченно                                    | Нативно                                            |
| Стоимость хранения      | Выше                                           | Ниже (объектное хранилище)                         |
| Сложность эксплуатации  | Ниже                                           | Выше                                               |
| Компетенции             | SQL, dbt                                       | Spark, Flink, Trino, Iceberg                       |
| Регуляторная отчётность | Сильная сторона                                | Требует дисциплины и governance                    |
| Совместимость с BI      | Высокая                                        | Высокая через Trino                                |

## Выбранный подход

### Промежуточное состояние (+3 месяца)

- **DWH на PostgreSQL** — основной аналитический компонент.
- Слои: `staging → core → marts`.
- Минимальные витрины: клиенты, счета, продукты, операции, обращения.
- Оркестрация — Airflow, трансформации — dbt.
- Lakehouse — только пилот (например, карточные события) или отсутствует.

### Целевое состояние (12 месяцев)

- **DWH на PostgreSQL** — регламентированная и управленческая отчётность.
- **Data Lakehouse (Iceberg + Trino)** — история транзакций, события каналов, архивные выгрузки, ML.
- **Trino** — федеративные запросы между DWH и Lakehouse.
- **Airflow** — оркестрация batch; **Spark/Flink** — обработка больших объёмов.

## Роль Apache Iceberg

- Открытый табличный формат для Lakehouse.
- ACID-транзакции поверх объектного хранилища.
- Schema evolution без перезаписи истории.
- Time travel и snapshots — для аудита и воспроизводимости.
- Совместимость с Spark, Flink, Trino — единый слой для batch и streaming.

## Роль Trino

- Федеративные SQL-запросы к DWH PostgreSQL, Lakehouse (Iceberg) и объектному хранилищу.
- Единая точка ad-hoc аналитики без копирования данных.
- Снижает нагрузку на OLTP: аналитики не ходят в Core/Cards/Loans.
- Используется BI и data science для кросс-доменных запросов.

## Что остаётся в DWH, что уходит в Lakehouse

| Данные                            | DWH PostgreSQL      | Lakehouse           | Почему                                 |
|-----------------------------------|---------------------|---------------------|----------------------------------------|
| Регламентированная отчётность     | ✔                   | —                   | ACID, предсказуемость, SLA             |
| Управленческая отчётность         | ✔                   | —                   | Стабильные витрины                     |
| Клиентские витрины (Customer 360) | ✔                   | частично            | DWH — для BI; Lakehouse — для ML-фичей |
| Счета и остатки                   | ✔                   | —                   | Небольшой объём, высокая критичность   |
| История транзакций                | частично (агрегаты) | ✔                   | Большой объём, time travel             |
| Карточные события                 | —                   | ✔                   | Событийные данные, streaming           |
| События каналов                   | —                   | ✔                   | Полуструктурированные                  |
| Архивные выгрузки после слияния   | —                   | ✔                   | Raw-слой bronze                        |
| Документы                         | —                   | объектное хранилище | Неструктурированные                    |
| ML-фичи и модели                  | —                   | ✔                   | Нативная поддержка                     |
| Справочники                       | ✔ (копия из RDM)    | —                   | Небольшой объём                        |

## Ограничения выбранного подхода

1. **Два хранилища** — нужна дисциплина, чтобы не дублировать данные без причины.
2. **Trino** — не замена DWH для тяжёлых регуляторных расчётов; используется для федеративных запросов.
3. **Iceberg** требует компетенций и управления метаданными (Nessie/Hive Metastore).
4. **Стоимость** — Lakehouse дешевле в хранении, но дороже в эксплуатации (Spark/Flink/Trino).
5. **Governance** — без DataHub и владельцев данные в Lakehouse быстро превращаются в «data swamp».
6. **Переходный период** — split-master означает, что до cutover в DWH консолидируются данные из двух источников; нужна
   сверка.
7. **Безопасность** — ПДн в Lakehouse требуют RBAC/ABAC, маскирования и DLP на всех слоях.
