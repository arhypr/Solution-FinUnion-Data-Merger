# Сравнение архитектурных вариантов

## Вариант 1. DWH на PostgreSQL

| Критерий             | Оценка                                                                                                                                                                         |
|----------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Плюсы                | Зрелость, ACID, знакомые компетенции, быстрый старт, низкая стоимость, простая регламентированная отчётность, хорошо для структурированных данных                              |
| Минусы               | Плохо масштабируется на большие объёмы истории и событий; нет нативного хранения полуструктурированных данных; ограниченная поддержка ML; дорогое вертикальное масштабирование |
| Когда подходит       | Средние объёмы, сильная структурированность, регламентированная отчётность, ограниченный бюджет                                                                                |
| Применимость к кейсу | **Высокая для промежуточного состояния и регуляторной отчётности**, но недостаточно для истории карточных операций и событийных данных после слияния                           |

## Вариант 2. Data Lakehouse

| Критерий             | Оценка                                                                                                                                                                                                |
|----------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Плюсы                | Единое хранилище для структурированных, полу- и неструктурированных данных; дешёвое масштабирование; поддержка ML; открытые форматы (Parquet, Iceberg); time travel; федеративные запросы через Trino |
| Минусы               | Сложнее в эксплуатации; нужны компетенции Spark/Flink/Trino; управление качеством и каталогом критично; не всегда оправдан для небольших объёмов                                                      |
| Когда подходит       | Большие объёмы истории, события, ML, неструктурированные данные, необходимость единого lakehouse                                                                                                      |
| Применимость к кейсу | **Высокая для целевого состояния**: история транзакций, карточные события, архивные выгрузки, ML для антифрода и риск-менеджмента                                                                     |

## Вариант 3. Data Mesh

| Критерий             | Оценка                                                                                                                                                         |
|----------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Плюсы                | Доменное владение, масштабирование по командам, data products с контрактами, снижение зависимости от центральной команды                                       |
| Минусы               | Требует зрелой data-культуры, федеративного governance, платформы self-service; высокий организационный риск; долгий старт; дублирование, если домены незрелые |
| Когда подходит       | Крупная организация с зрелыми доменными командами и сильным Data Office                                                                                        |
| Применимость к кейсу | **Частичная**: элементы Data Mesh (data products, владельцы, контракты) применимы, но полный mesh после слияния двух банков — рискованно                       |

## Выбор: гибридная архитектура

**Целевой подход — гибрид:**

1. **DWH на PostgreSQL** — ядро регламентированной и управленческой отчётности. Это то, что нужно через 3 месяца и что
   остаётся в целевом состоянии для регуляторики.
2. **Data Lakehouse (Iceberg + Trino)** — история, события, полуструктурированные данные, ML, архивные выгрузки.
3. **Элементы Data Mesh** — 5 доменных data-продуктов с владельцами и контрактами, но платформа и governance
   централизованы (Data Office).
4. **MDM + RDM** — единые мастер-данные.
5. **Integration Layer (ESB + Kafka + CDC)** — единая точка маршрутизации.

### Почему гибрид

- Невозможно за 3 месяца построить Lakehouse для всей организации — нужен быстрый результат (DWH PG).
- Регуляторная отчётность требует предсказуемости и ACID — PostgreSQL DWH это даёт.
- История карточных операций и событийные данные не помещаются эффективно в PostgreSQL — Lakehouse решает.
- Полный Data Mesh после слияния — организационный риск; data products дают пользу без полной децентрализации.
- BIAN-домены естественно ложатся на границы data products и мастер-систем.

### Отклонённые варианты

- **Только DWH PG** — не выдержит объёмов истории и ML-сценариев.
- **Только Lakehouse** — избыточен для регуляторики и повышает риск SLA отчётности.
- **Полный Data Mesh** — преждевременен: нет зрелых доменных команд и федеративного governance.
